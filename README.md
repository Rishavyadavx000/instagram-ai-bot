# instagram-ai-bot

An Instagram webhook service that replies to DMs (and optionally comments) with short,
natural **Hinglish** replies generated by an AI provider, using the official **Instagram
API with Instagram Login** (`graph.instagram.com`). Built with Node.js + Express, no
database, minimal dependencies.

## Features

- `GET /webhook` — Meta webhook verification (hub challenge/response)
- `POST /webhook` — receives message + comment events, acknowledges instantly (HTTP 200),
  processes asynchronously so slow AI calls never cause Meta to retry
- Defensive payload parsing — doesn't assume a fixed nesting, logs and skips anything
  unrecognized instead of crashing
- AI-generated Hinglish replies (OpenAI), with a static fallback when AI is disabled or
  unavailable
- Comment auto-reply, behind its own feature flag
- Message reactions (❤️), behind its own feature flag, with a graceful no-op when an
  event type doesn't support it
- In-memory duplicate-event protection (never replies twice to the same message/comment)
- No secrets ever hard-coded, logged, or exposed via any HTTP endpoint

## Prerequisites

- An **Instagram Business or Creator account**
- A **Meta Developer app** with the Instagram product added, using **Instagram API with
  Instagram Login** (no Facebook Page required for this flow)
- An Instagram User access token with `instagram_business_basic` +
  `instagram_business_manage_messages` (and `instagram_business_manage_comments` if you'll
  enable comment replies)
- An OpenAI API key (optional — the bot runs fine without one, using the fallback reply)
- Node.js 18+

## Setup

```bash
npm install
cp .env.example .env
# fill in .env with your real values
npm start
```

The server starts even if `OPENAI_API_KEY` or the Instagram credentials are missing — it
logs a warning for whichever pieces aren't configured yet instead of crashing. Check
`GET /status` to see what's live.

For local webhook testing, expose your local server with a tunnel (e.g. `ngrok http 3000`)
since Meta needs a public HTTPS URL to send webhooks to.

## Environment variables

| Variable | Required | Notes |
|---|---|---|
| `PORT` | no | defaults to `3000` |
| `VERIFY_TOKEN` | yes, for webhook verification | any secret string you choose |
| `INSTAGRAM_ACCESS_TOKEN` | yes, to send replies | never commit this |
| `INSTAGRAM_USER_ID` | yes, to send replies | the IG professional account's own id |
| `META_GRAPH_BASE_URL` | no | defaults to `https://graph.instagram.com` |
| `GRAPH_API_VERSION` | no | defaults to `v26.0` — Meta ships new versions periodically, check [the docs](https://developers.facebook.com/docs/instagram-platform) if calls start failing |
| `OPENAI_API_KEY` | no | AI replies fall back to a static message if unset |
| `OPENAI_MODEL` | no | defaults to `gpt-4o-mini` |
| `AI_ENABLED` | no | defaults to `true` |
| `AUTO_REPLY_ENABLED` | no | defaults to `true` |
| `AUTO_COMMENT_REPLY_ENABLED` | no | defaults to `false` |
| `AUTO_REACTION_ENABLED` | no | defaults to `false` |
| `DEFAULT_REPLY_LANGUAGE` | no | defaults to `hinglish` |

## Configuring the Meta App webhook

1. In the App Dashboard, add a Webhooks subscription for **Instagram**.
2. Callback URL: `https://<your-deployed-domain>/webhook`
3. Verify token: same value as `VERIFY_TOKEN` in your `.env`.
4. Subscribe to the `messages` field (and `comments` if you'll use comment auto-reply).
5. Meta calls `GET /webhook` once to confirm; this project handles that automatically.

Note the messaging window: your app can only message a user who has messaged the
Instagram account first, and only within 24 hours of their last message (longer, with
restrictions, using the Human Agent tag) — this is a platform-level rule, not something
this code can bypass.

## Deploying to Render

1. Push this project (including `src/`, `.env.example`, and `.gitignore`, but **not** a real
   `.env`) to a GitHub repository.
2. In the Render dashboard: **New → Web Service**, then connect that repository.
3. Fill in the service form:
   - **Name**: anything, e.g. `instagram-ai-bot`
   - **Region**: closest to you or your users
   - **Branch**: `main` (or whichever you deploy from)
   - **Root Directory**: leave blank (this project's `package.json` is at the repo root)
   - **Runtime**: `Node`
   - **Build Command**: `npm install`
   - **Start Command**: `npm start`
   - **Instance Type**: `Free` is enough to start; note that free instances spin down when
     idle, which adds latency to the first webhook after a period of inactivity
4. Under **Environment → Environment Variables**, add every key from `.env.example` with
   your real values (`PORT` can be left out — Render sets it automatically and `config.js`
   reads whatever Render provides).
5. Optional but recommended: under **Settings → Health Check Path**, set `/health` so
   Render can detect a healthy deploy automatically.
6. Click **Create Web Service**. Render installs, builds, and starts the app; watch the
   **Logs** tab for the `[startup] configuration status: ...` line to confirm every piece
   is configured the way you expect.
7. Once live, take the resulting `https://<your-service>.onrender.com/webhook` URL and use
   it as the callback URL in the Meta App Dashboard's webhook subscription (see the section
   above) — the verify token there must match `VERIFY_TOKEN` in Render's environment
   variables exactly.
8. The server binds to `0.0.0.0` and reads `process.env.PORT` directly, which is what
   Render's platform requires — no extra configuration needed for that part.

## Production notes

- **Duplicate protection is in-memory and single-instance.** It resets on restart and
  isn't shared across multiple instances. If you scale beyond one instance, replace
  `src/dedupe.js` with a shared store (Redis `SETNX` + TTL, or a DB table with a unique
  constraint on the event/message id).
- **No automatic retries** on failed outbound sends, by design — retrying could cause
  duplicate replies. Failures are logged with a redacted id so you can monitor them.
- **Rate limits**: the Graph API is rate-limited per app/account; the Messaging API's
  throughput is tracked separately from other Graph API calls. Normal reply volume from
  real conversations is unlikely to hit this, but keep an eye on `429` responses in logs.
  On a `429`, this project does not auto-retry — it logs and moves on.
  This bot's automation only replies to conversations users start — it never
  initiates messages to people who haven't contacted the account, and does not send
  comment replies or reactions unless their feature flags are explicitly enabled.
- Depending on where your users are and how you present the bot, you may want to disclose
  that replies are automated — check applicable local rules on automated messaging
  disclosure for your audience.
